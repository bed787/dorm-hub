# Проверка проекта и безопасности — 17 октября 2026

Проверена доступная копия Dorm Hub со всеми последними исправлениями из этой переписки. Просмотрены исходники сервера и интерфейса, SQL и миграции, Docker и GitHub Actions. На публичном сайте выполнялись только обычные запросы HEAD: атакующие сценарии проверялись локально на отдельной базе.

## Основной результат

В проверенных сценариях не найден обход авторизации, получение прав администратора, доступ к чужим черновикам/фотографиям или изменение чужих объявлений. Это результат конкретных проверок, а не гарантия отсутствия всех уязвимостей.

Найдены и исправлены проблемы зависимостей, обход лимита архива, накопление просроченных записей и ошибка справочника. Убраны неиспользуемый путь удаления файлов и перекрытые CSS-правила. Настройки ротации Docker-логов подготовлены отдельно: для действующего VPS их нужно применить вручную.

## Что исправлено

| Проблема | Последствие | Изменение |
|---|---|---|
| Старый `golang.org/x/text` 0.29.0 | Сканер находил известные ошибки в используемых функциях библиотеки | Обновлён до 0.41.0; зависимый `x/sync` — до 0.22.0 |
| Локальная проверка выполнялась на Go 1.27.1; Docker использовал плавающий тег 1.27 | Результат сборки зависел от актуального содержимого тега; сканер отмечал ошибки стандартной библиотеки | В go.mod, Docker и CI закреплён Go 1.27.2. В CI добавлен govulncheck 1.9.0 до публикации образа |
| Лимит 50 архивных объявлений проверялся только при создании черновика | Можно было создать обычное объявление и отправить его в архив сверх лимита, в том числе через сохранение | Общая проверка вызывается при каждом пользовательском переходе в архив. | Просроченные коды входа не очищались автоматически; истёкшие сессии очищались только при следующем входе того же пользователя | Лишние служебные и персональные данные могли копиться в БД | Ежеминутная очистка ограниченными порциями: истёкшие сессии и коды, истёкшие больше часа назад. | Очередь очистки файлов обрабатывалась рекурсивно | Большая очередь делала управление длительностью менее понятным | Обычный цикл, проверка отмены контекста; фоновый проход ограничен пятью секундами |
| Повторные CSS-переопределения | Размеры и оформление приходилось искать в нескольких местах | Удалены 68 перекрытых объявлений свойств и 20 опустевших правил. Комментарии и медиаправила сохранены |
| В .gitignore были перечислены исходные конфигурации и Go-модули | Нужные файлы легко забыть включить в коммит; раньше приходилось использовать git add -f | Убраны исключения для go.mod, go.sum, Compose и Makefile. Исключения для .env, данных и локальных файлов сохранены |
| Для HTTPS-ответов не задавался HSTS | Браузеру не сообщалась политика использования HTTPS для последующих посещений | Заголовок добавляется только для production с HTTPS; локальная разработка его не получает |

Отклонение модератором остаётся возможным и при полном архиве: отказ не должен превращаться в невозможность убрать объявление из очереди. Это может временно увеличить архив сверх 50, но дополнительные пользовательские записи после этого не принимаются до освобождения места.

## Что показал сканер зависимостей

Первый локальный запуск govulncheck отметил 12 известных проблем в достижимых функциях x/text и стандартной библиотеки Go. Наличие пути вызова не доказывает возможность эксплуатации через сайт. В частности, HTTP/2 и TLS снаружи обрабатывает отдельный Caddy, а часть функций x/text используется для соединения с БД.

Версию компилятора уже работающего контейнера я не определял. Плавающий Docker-тег мог уже содержать более свежий Go, чем локальная среда. Поэтому число 12 нельзя трактовать как «12 подтверждённых способов взломать работающий сайт».

После обновления Go до 1.27.2 и зависимостей повторный запуск завершился: **No vulnerabilities found**. Это относится к проверенной сборке и базе уязвимостей, доступной во время запуска.

## Проверки доступа и обработки данных

- Вход: разрешённые адреса, одноразовость OTP, срок действия, пять попыток, ограничение повторных писем, отдельный административный вход.
- Права: гость/участник/администратор, отзыв роли, блокировка аккаунта, доступ во время техработ. Поле is_admin из клиентского JSON не принимается.
- IDOR: чтение, изменение, удаление и смена статуса чужого объявления; административные фильтры и маршруты из обычной сессии; доступ к чужим фото проверяется отдельно.
- CSRF: чужой Origin и неверный токен отвергаются. Наличие кнопки или знание адреса админского API прав не дают.
- SQL: значения передаются параметрами; пользователь не задаёт SQL-сортировку или имена таблиц. Поисковая строка с SQL-подобным содержимым не раскрывает чужие данные и не меняет запрос.
- XSS: пользовательский текст экранируется при выводе; сообщения журнала отображаются как текст. Контактные ссылки опубликованных объявлений допускаются только на HTTPS-домены Telegram/VK. Неполные контакты черновика не выдаются как публичные кнопки.
- Фотографии: проверяется фактический формат JPEG/PNG, размер и число пикселей; файл перекодируется в JPEG. SVG и произвольные данные не принимаются. Имена создаёт сервер, обход каталогов ограничен строгой проверкой имени.
- Ограничения: число публикаций, архив, квота фотографий и число одновременных загрузок; повторы создания и загрузки не дублируют данные.
- Удаление: данные аккаунта и связанные записи удаляются транзакционно, файлы проходят надёжную очередь. Права доступа к фото исчезают с удалением записей.
- Журнал админки не получает тела запросов, cookie, коды и произвольные атрибуты с почтами/секретами.
- Деплой: SSH-команда ограничена, digest проверяется, входящие команды не выполняются через eval; секреты окружения не включаются в Docker-контекст.

## Как проверялось

Два дефекта воспроизведены тестами на исходных реализациях: обход архива и ошибка целого номера общежития. После исправлений те же проверки проходят.

Пройдены: все Go-тесты с race detector и интеграционными сценариями на отдельной PGlite; 40 Node-тестов; go vet; сборка приложения; повторный govulncheck; разбор YAML/CSS и bash -n скриптов деплоя. Сравнение вычисленных стилей в JSDOM совпало в 16 сочетаниях ширины 320/420/760/1440, светлой/тёмной темы и настройки анимации.

Дополнительно проверен интерфейс через JSDOM с настоящим HTTP, изолированной БД и тестовым SMTP: вход, документы, работающие сессии, техработы и админский журнал с фильтрами.

Снаружи сайт ответил по HTTPS, HTTP и www перенаправлялись на основной HTTPS-адрес; присутствовали CSP, nosniff, Referrer-Policy и Permissions-Policy. В этот момент главная отдавала 200. HSTS входит в новое обновление.

## Пределы проверки и оставшиеся вопросы

- PGlite не заменяет настоящую PostgreSQL для всех конкурентных ситуаций. Проверка с PostgreSQL 17 включена в GitHub Actions и выполнится после пуша. Новый workflow в реальном GitHub из этой среды ещё не запускался.
- Полноценного визуального прогона Chrome/Safari и внешнего сканирования атак Burp/ZAP не было. На production не создавались аккаунты, не отправлялись коды и атакующие запросы.
- Нет доступа к реальным .env.production, firewall, резервным копиям, журналам VPS и установленному Caddy. Их защищённость и актуальность этим отчётом не подтверждаются.
- TRUSTED_PROXY_CIDRS в шаблоне пуст. Если на VPS он тоже пуст, посетители за Caddy делят лимит попыток по адресу прокси. Нужен точный непосредственный адрес прокси, который видит приложение; нельзя просто разрешить X-Forwarded-For от всех адресов. Настройку нельзя достоверно подобрать по исходникам без проверки сети VPS.
- Права администратора сохраняются в БД. Удаление адреса из ADMIN_EMAILS само по себе не снимает уже выданную роль is_admin.
- Подтверждение владения Telegram/VK технически не реализовано: правила и ручная модерация не заменяют такую проверку.
- app.js остаётся крупным файлом. Следующий полезный шаг в структуре — выделить редактор объявлений с его состоянием и очередью сохранений в отдельный модуль. Сейчас он покрыт проверками; полная смена архитектуры для этого обновления не требуется.

## Применить обновление приложения

Скачай dorm-hub-security-review.zip в «Загрузки». На Mac:

```bash
cd ~/Desktop/projects/dorm-hub &&
unzip -o ~/Downloads/dorm-hub-security-review.zip -d . &&
git add .gitignore Dockerfile go.mod go.sum compose.production.yaml internal web tests docs deploy .github/workflows/deploy.yml &&
git commit -m "Harden dependencies, quotas and cleanup; simplify styles" &&
git push
```

Новых миграций нет. Режим техработ, причина и пользовательские данные сохранятся. Сборке нужен Go 1.27.2; для сервера его устанавливает Docker-образ, отдельно ставить Go на VPS не нужно. Дождись зелёного GitHub Actions.

## Отдельно применить ротацию логов на действующем VPS

Push обновляет образ приложения, но не установленный /etc/dorm-hub/compose.registry.yaml. Следующие команды выполняются отдельно. Пересоздание контейнера БД вызовет короткий перерыв подключения; том с базой сохраняется.

На Mac, после распаковки:

```bash
cd ~/Desktop/projects/dorm-hub &&
scp deploy/compose.registry.yaml root@157.228.138.75:/opt/dorm-hub/compose.registry.review.yaml
```

На сервере:

```bash
cd /opt/dorm-hub &&
APP_IMAGE="$(cat /var/lib/dorm-hub-deploy/current-image)" docker compose --env-file .env.production -f compose.registry.review.yaml config --quiet &&
cp -a /etc/dorm-hub/compose.registry.yaml /etc/dorm-hub/compose.registry.yaml.before-review &&
install -m 600 compose.registry.review.yaml /etc/dorm-hub/compose.registry.yaml &&
APP_IMAGE="$(cat /var/lib/dorm-hub-deploy/current-image)" docker compose --project-name dorm-hub --project-directory /opt/dorm-hub --env-file .env.production -f /etc/dorm-hub/compose.registry.yaml up -d --no-build --pull never --wait --wait-timeout 120
```

Проверить результат на сервере:

```bash
docker inspect --format '{{json .HostConfig.LogConfig}}' dorm-hub-app-1 dorm-hub-db-1
```

Нужен тип local, max-size 10m и max-file 3. Перед заменой остаётся копия прежней конфигурации. Команды не удаляют volumes и не меняют пароли.
